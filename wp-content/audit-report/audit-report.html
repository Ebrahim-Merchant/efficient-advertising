🚨 Critical Issues (5)

Critical C-01 — SQL Injection Vulnerability in payement.php

File: wp-content/themes/Efficient/payement.php

Description: All form fields from $_POST are inserted directly into a raw SQL query using $wpdb->query() with string concatenation and no sanitization, escaping, or prepared statements. An attacker can manipulate any form field to execute arbitrary SQL commands against the database, leading to data theft, privilege escalation, or full database destruction.

// VULNERABLE CODE (current)
$Name = $_POST['Name'];
$wpdb->query("INSERT INTO $table_name(...) VALUES('$Name','$Company',...)");
✅ Fix Applied

Replace raw query with $wpdb->prepare() and sanitize all inputs with sanitize_text_field() and is_email(). CSRF nonce validation added.

// FIXED CODE
if (!isset($_POST['payment_nonce']) || !wp_verify_nonce($_POST['payment_nonce'], 'payment_form_action')) {
    wp_die('Security check failed.');
}
$Name = sanitize_text_field($_POST['Name']);
$Email = sanitize_email($_POST['Email']);
$wpdb->insert($table_name, [
    'name' => $Name, 'email' => $Email, ...
], ['%s','%s',...]);
Critical C-02 — No CSRF Protection on Payment Form

File: wp-content/themes/Efficient/payement.php

Description: The payment form has no WordPress nonce field. Any malicious third-party site can trick a logged-in user into submitting the payment form, causing fraudulent payment records or unauthorized PayPal redirect with attacker-controlled amounts.

✅ Fix Applied

Added wp_nonce_field('payment_form_action', 'payment_nonce') to the form and nonce verification at the top of the processing block.

Critical C-03 — WordPress Version Disclosed via readme.html

File: readme.html (site root)

Description: The readme.html file is publicly accessible and discloses the WordPress version number. Attackers use this to identify known CVEs for the specific version and craft targeted exploits.

✅ Fix Applied

Added .htaccess rule to block direct access to readme.html, license.txt, and wp-config-sample.php.

Critical C-04 — Suspicious File: YuQ.js.php in Theme Directory

File: wp-content/themes/Efficient/YuQ.js.php

Description: A randomly named PHP file with a .js.php double extension exists in the theme directory. While currently empty, this naming pattern is a hallmark of web shell backdoors — attackers often plant empty files as placeholders and inject malicious code later, or test if uploads are executable. This file has no legitimate purpose in the theme.

✅ Fix Applied

File deleted from the theme directory. Recommend running a full malware scan with MalCare or Wordfence.

Critical C-05 — Missing WordPress .htaccess Rewrite Rules

File: .htaccess (site root)

Description: The .htaccess file contains only LiteSpeed Cache configuration. The standard WordPress rewrite block (# BEGIN WordPress ... # END WordPress) is completely absent. On any Apache-based server (e.g., production cPanel hosting), WordPress permalinks will be completely broken — all non-root URLs will return 404 errors. Additionally, missing standard rules means there is no wp-config.php direct access block at the Apache level.

✅ Fix Applied

Standard WordPress rewrite block and security hardening rules added to .htaccess.

⚠️ High Severity Issues (8)

High H-01 — WP File Manager Plugin (Known Critical CVE History)

Plugin: wp-file-manager v7.2.5

Description: WP File Manager has a history of critical unauthenticated remote code execution vulnerabilities (e.g., CVE-2020-25213). This plugin provides a full filesystem browser inside WordPress admin. Even at v7.2.5, it represents a high-value attack target. If admin credentials are ever compromised, an attacker gains complete server file access.

⚠️ Recommendation

Strongly recommended to deactivate and delete this plugin. Use hosting-level FTP/SFTP or cPanel File Manager instead. If it must remain, restrict it to administrator role only and ensure it is updated.

High H-02 — Duplicate & Conflicting Security Plugins

Plugins: Wordfence Security v7.11.4 + MalCare Security v5.53

Description: Both Wordfence and MalCare are comprehensive security/firewall plugins. Running both simultaneously causes firewall rule conflicts, double resource consumption, potential false positives, and unclear security ownership. Each hooks into the same WordPress lifecycle events, causing performance degradation and unpredictable behavior.

✅ Recommendation

Keep one security plugin. Wordfence is recommended for on-server scanning. Deactivate and delete the other.

High H-03 — Payment redirect URL points to old Demo Domain

File: wp-content/themes/Efficient/payement.php (lines 42–43)

Description: Both the PayPal return and cancel_return URLs are hardcoded to https://efficient.demoshowcase.in/payment/ — an old demo/staging domain. After a PayPal payment, users are redirected to a domain that no longer belongs to the site owner, potentially exposing users to phishing or confusion.

✅ Fix Applied

Replaced hardcoded demo domain with home_url('/payment/') to use the current site's domain dynamically.

High H-04 — Duplicate Google Analytics Code in header.php

File: wp-content/themes/Efficient/header.php

Description: The Google Analytics tracking code (UA-166007422-1 + AW-854448823) is hardcoded twice in header.php — once before wp_head() and once after it. This causes double-counting of all pageviews and conversion events, corrupting all analytics data and Google Ads conversion reporting.

✅ Fix Applied

Removed the duplicate block after wp_head(). Retained the block before wp_head() (the first occurrence).

High H-05 — Universal Analytics (UA-) Is Discontinued Since July 2023

File: wp-content/themes/Efficient/header.php

Description: The theme still uses Universal Analytics (UA-166007422-1). Google shut down Universal Analytics properties in July 2023 — no data has been collected since then. The tag is firing on every page load but recording nothing. All analytics data for the past ~2.5 years has been lost.

✅ Recommendation

Replace the Universal Analytics tag with a Google Analytics 4 (GA4) measurement ID (G-XXXXXXXXXX format) and update the Google Ads conversion tracking for GA4.

High H-06 — Outdated jQuery 3.3.1 Bundled in Theme

File: wp-content/themes/Efficient/header.php

Description: Theme manually loads jquery-3.3.1.min.js from the theme's /js/ folder. This version is from 2018 and has known XSS vulnerabilities. Additionally, loading a custom jQuery alongside WordPress's own registered jQuery causes version conflicts and double-loading.

✅ Recommendation

Remove manual jQuery script tag. Use WordPress's built-in jQuery by calling wp_enqueue_script('jquery') in functions.php, which loads the version bundled with WordPress core (current, security-patched).

High H-07 — error_log File in Theme Directory Exposes Server Paths

File: wp-content/themes/Efficient/error_log

Description: A PHP error_log file exists in the theme directory and is publicly readable. It exposes full server filesystem paths (e.g., /home3/cugcqgmy/public_html/efficient/ and /home/efficientadvtcom060/public_html/), WordPress file structure, and PHP fatal error details. Attackers use this to map the server and craft targeted path traversal or file inclusion attacks.

✅ Fix Applied

Deleted the error_log file. Added .htaccess rule to block web access to all error_log files across the site.

High H-08 — Google Ads Conversion Script Fires on All Pages

File: wp-content/themes/Efficient/header.php

Description: The Google Ads conversion snippet (AW-854448823/LuqOCKjBmKMBELe1t5cD) is placed in the global header, causing it to fire on every single page load — not just on the actual conversion confirmation page. This inflates Google Ads conversion counts massively, resulting in incorrect bidding decisions and wasted ad spend.

✅ Fix Applied

Removed the conversion event snippet from the global header. It should only be on the thank-you/confirmation page template.

⚠️ Medium Severity Issues (9)

Medium M-01 — Default WordPress Table Prefix (wp_)

File: wp-config.php

Description: The database table prefix is the default wp_. Automated SQL injection tools specifically target this prefix. Changing it makes mass SQL injection attacks less effective.

Recommendation

On a new install: change $table_prefix to a custom value (e.g., ea7x_). On an existing site, requires database migration — use a plugin like "Brozzme DB Prefix" with caution. Not auto-fixed due to risk of data loss.

Medium M-02 — Orphaned Hostinger Plugin Files

Files: wp-content/plugins/hostinger-mu-plugin.php, wp-content/plugins/hostinger-preview-domain.php

Description: These are orphaned files from a previous Hostinger hosting migration. They are not in plugin subdirectories and serve no function on the current hosting. They may interfere with plugin scanning or be flagged as unknown files by security systems.

✅ Recommendation

Delete both orphaned files. They have no use in this environment.

Medium M-03 — Conflicting Cache Plugins (LiteSpeed Cache + SpeedyCache)

Files: wp-content/advanced-cache-backup.php (SpeedyCache), LiteSpeed Cache plugin active

Description: SpeedyCache's advanced-cache.php (backed up as advanced-cache-backup.php) indicates SpeedyCache was previously installed. LiteSpeed Cache is now active. Having remnants of two cache plugins can cause WP_CACHE conflicts, stale cache issues, and unpredictable behavior.

✅ Recommendation

Ensure SpeedyCache is fully removed. Delete advanced-cache-backup.php. Only LiteSpeed Cache should be active.

Medium M-04 — Migration/Export Plugins Left Active

Plugins: All-in-One WP Migration (7.81), WP Migrate DB (2.7.6)

Description: Both migration plugins are installed. These plugins can expose database backups and site exports if left active on a live server. They are high-value targets for attackers looking to steal database credentials and full site content.

Recommendation

Deactivate and delete both migration plugins when not actively migrating. Use UpdraftPlus (already installed) for backups instead.

Medium M-05 — local-xdebuginfo.php Exposed in Public Root

File: local-xdebuginfo.php (site root)

Description: This LocalWP debug file calls xdebug_info() which outputs detailed PHP configuration, loaded extensions, server environment variables, and filesystem paths. This must never be accessible on a production server.

✅ Fix Applied

Added .htaccess rule to block web access to local-xdebuginfo.php. File should be deleted before going to production.

Medium M-06 — index.php-old Leftover File in wp-content

File: wp-content/index.php-old

Description: Non-standard leftover file. Indicates a manual file operation was performed without cleanup. Such files can contain old code or become a source of confusion during security audits.

✅ Recommendation

Delete wp-content/index.php-old.

Medium M-07 — DB_CHARSET Set to utf8 Instead of utf8mb4

File: wp-config.php

Description: The database charset is utf8, which is MySQL's 3-byte UTF-8 and cannot store 4-byte Unicode characters (emojis, certain Asian scripts, special symbols). WordPress recommends utf8mb4 since WP 4.2. Using utf8 can cause data truncation or errors when saving content with emojis or special characters.

✅ Fix Applied

Changed DB_CHARSET from 'utf8' to 'utf8mb4' in wp-config.php.

Medium M-08 — Missing Security HTTP Headers

File: .htaccess

Description: The site sends no security-focused HTTP response headers: no X-Frame-Options (clickjacking protection), no X-Content-Type-Options (MIME sniffing), no Referrer-Policy, and no Permissions-Policy. These headers are recommended by OWASP and expected by modern browsers.

✅ Fix Applied

Added security headers to .htaccess.

Medium M-09 — PHP Fatal Errors in Theme error_log (Historical)

File: wp-content/themes/Efficient/error_log

Description: The error log records multiple PHP fatal errors: Call to undefined function get_header() in index.php. This means the theme's index.php was accessed directly (bypassing WordPress bootstrap), causing crashes. This has occurred across multiple hosting environments and dates (2022–2025), indicating a recurring issue.

✅ Fix Applied

Added ABSPATH guard at the top of theme PHP files to prevent direct access.

File: wp-content/themes/Efficient/inc/options-framework.php

Description: An ancient Options Framework library (v1.9.1, 2014) is bundled inside the theme. It is no longer actively maintained and may not be fully compatible with modern WordPress APIs.

Recommendation

Evaluate migrating theme options to the WordPress Customizer API or ACF Options Page for modern compatibility.

Low L-04 — maintenance.php in wp-content (503 Page)

File: wp-content/maintenance.php

Description: A maintenance page file exists in wp-content/. While this is standard for the WP Maintenance plugin, keeping an active 503 maintenance file when the site is not under maintenance can cause issues if accidentally triggered.

Recommendation

Verify the maintenance plugin is deactivated when not in use.

Low L-05 — Robots.txt / Security.txt Not Configured

Description: No robots.txt file exists in the root (WordPress generates a dynamic one, but it does not block sensitive paths like /wp-admin/, /wp-login.php from indexing bots). No security.txt is present either.

Recommendation

Configure a proper robots.txt via Yoast SEO (already installed). Consider adding a /.well-known/security.txt file.

Low L-06 — Google Tag Manager Duplicate dataLayer Declarations

File: wp-content/themes/Efficient/header.php

Description: Multiple window.dataLayer = window.dataLayer || []; declarations exist because each gtag.js script block reinitializes the data layer and gtag function. This is redundant but not harmful. However, it indicates the tracking setup was not implemented using GTM best practices.

Recommendation

Consolidate all tracking through Google Tag Manager (single GTM snippet) rather than hardcoding multiple gtag.js scripts.
